# 多版本开发骨架

用户要求：同一项目维护 Minecraft 1.21.11、26.3 的 Paper 插件与 Fabric 客户端模组；已有玩法和辅助功能随后从旧工程照搬，不重新实现。

## 方案与边界

采用 Gradle Kotlin DSL 单仓库、多模块、每版本独立产物。公共源码共享编译，版本 API 差异留在版本模块。该选择为骨架的工程默认值，用户可后续调整。

单 JAR 跨版本会把 Java 21 / 25 和客户端映射差异带入运行时；两份完整项目则会重复玩法代码。这两种方案均不适合作为当前默认。

## 结构

- `common`：Java 21，预留纯 Java 公共逻辑。
- `protocol`：Java 21，预留原项目协议，当前不定义频道、数据包或握手。
- `paper/shared`、`fabric/shared`：公共入口和元数据模板。
- `paper/1.21.11`、`paper/26.3`：Java 21 / 25，分别依赖对应 Paper API。
- `fabric/1.21.11`：Java 21、remap Loom、Mojang mappings。
- `fabric/26.3`：Java 25、非 remap Loom，无 mappings 依赖。

公共模块编入四个发布 JAR，不要求玩家或服务器额外安装内部模块。客户端只声明 client 入口。版本模块默认源码目录用于后续放置适配代码，当前不预建适配接口。

## 开发与验证

使用带校验和的 Gradle Wrapper；依赖集中到版本目录。默认构建全部目标，`-PmcVersion` 可仅配置一个版本，未知版本立即报错。CI 按版本构建，安装 JDK 21 和 25。

验收：四个模块均可编译打包；检查元数据展开、入口 class、Java 字节码版本、1.21.11 的 remap 产物。真实游戏的加载、连接和玩法测试需在迁移后另行进行，不以编译通过替代。

## 待迁移时确认

旧工程的具体路径、功能清单、对外名称与旧协议保持策略。相邻旧工程当前只作为构建配置参考，不迁入任何玩法实现。

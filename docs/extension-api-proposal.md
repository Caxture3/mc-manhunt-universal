# 扩展 API 原始设计建议

目标是让依赖插件能够组合玩法，同时由核心维护角色、淘汰、追踪和展示的一致性。本文保留最初设计思路；公共 API 1.0.0 已按后续要求实现，准确签名与接入方式以[开发者指南](extension-api.md)和 SDK Javadoc 为准。默认模式仍每局固定身份。

## 优先开放的能力

| 能力 | 建议接口 | 必要内容 |
| --- | --- | --- |
| 只读对局查询 | `ManhuntUniversalApi.matches()` | 当前对局快照、sessionId、状态、参与者 UUID、角色、是否淘汰、开始时间、目标末地、版本号。返回不可变快照。 |
| 对局控制 | `MatchController.start/stop/finish` | 复用现有开局校验、倒计时、重置、结算与清理；返回明确成功/拒绝原因。`stop` 取消对局，`finish` 记录胜方与原因。 |
| 原子角色分配 | `RoleController.assign/reroll` | 指定完整角色分配，或对符合条件的玩家随机重抽。统一校验并同步所有依赖状态，支持来源插件和变更原因。 |
| 对局和角色事件 | `MatchStartedEvent`、`MatchEndedEvent`、`RolesChangingEvent`、`RolesChangedEvent` 等 | 依赖插件可监听正式开始、所有终止路径、变更前后、淘汰、进入目标末地。变更前事件可取消，完成后事件只通知。 |
| 淘汰与胜负扩展 | `ParticipantController`、`EliminationPolicy`、`VictoryPolicy` | 标准淘汰/恢复入口；在默认死亡淘汰和判胜之前允许已注册玩法策略接管，避免核心先结束对局。 |
| 扩展注册和版本查询 | `apiVersion/capabilities`、`ExtensionRegistration` | 记录所属插件、策略所有权和注销句柄；禁用时注销其策略。多个插件争夺角色/判胜控制时明确拒绝冲突，不靠调用先后决定。 |

第一版建议先完成这些接口。指南针自定义目标、额外客户端界面、任意新角色体系可在出现实际需求后扩展。

## 角色变更必须是一个完整操作

当前 `GameSession` 的速通者名单为不可变字段，且淘汰、旁观模式、指南针授权、位置缓存、Tab/名称牌及结算都依赖它。把列表公开或添加一个 setter 无法安全支持轮换。

建议 `assign` 与 `reroll` 接收预计 sessionId；有竞争需求时再携带快照修订号。它们在服务器主线程上完成：

1. 验证本局仍在运行、来源拥有控制权、参与者有效、名单不重复且至少保留一名猎人和一名速通者。
2. 创建完整候选分配，触发可取消的变更前事件；拒绝或取消时不产生副作用，防止事件中重入重复修改。
3. 提交新的权威角色状态，重建猎人/速通者关系；按明确策略处理淘汰与旁观状态。
4. 撤销旧指南针选择授权，清理不再适用的追踪缓存和绑定物品，补发新角色物品。
5. 按当前隐藏配置更新个人提示、身份颜色与客户端显示，完成后通知角色已变更事件。

参数失败应返回如 `STALE_SESSION`、`INVALID_STATE`、`INVALID_ASSIGNMENT`、`CANCELLED`、`CONTROL_CONFLICT` 的结果，不能静默忽略或只修改一部分名单。查询快照不能用于绕开这些入口直接修改内部对象。

建议默认只对未淘汰且当前可参与的玩家重抽，淘汰者不会因角色轮换自动复活；复活由单独的标准恢复操作控制。对局级末地解锁和目标末地默认继续保留，开局重置不随角色重抽重复执行。这些属于后续 API 落地时需要明确的玩法策略。

`force-random-roles` 继续控制玩家的开局预约，`hide-role-assignments` 继续控制展示。扩展变更也必须复用隐藏规则；默认模式在没有扩展请求时仍每局身份固定。

## 事件和策略的边界

建议至少提供以下事件：

- 开局准备（可取消）、开始倒计时、正式开始。
- 对局结束：含正常胜负、管理员停止、倒计时取消、插件停用，保证每局至多一次，携带终止原因。
- 角色变更前（可取消）与变更后：携带旧/新分配、来源和原因。
- 玩家淘汰前（允许策略阻止标准淘汰）与淘汰后、恢复后。
- 首次存活速通者进入目标末地。
- 即将判胜：在核心不可逆结算前供注册策略决定保留默认结果、暂缓或替换结果。

通知事件用于观察，策略接口用于决定玩法。仅有“玩家已死亡/对局已结束”通知无法实现自定义失败条件，因为默认失败处理此时已经发生。管理停止和插件停用仍须可靠执行清理，不能被玩法策略无限阻止。

## 随机轮换插件如何使用

1. 监听正式开始，记录 sessionId，启动自己管理的随机时间任务。
2. 到时查询当前快照，确认仍是同一局且处于 RUNNING，调用 `roles().reroll(...)`。
3. 成功后再抽下一次等待时间；被取消或冲突时按明确策略处理。
4. 监听所有对局终止路径，或在扩展插件禁用时取消任务并注销策略。

随机间隔和轮换次数由扩展插件管理，核心负责正确提交一次角色变更。无需为这种服务端玩法增加 Fabric 协议。

## 包和依赖建议

- 根入口与稳定接口放在 `com.caxture.manhuntuniversal.api`；内部 `game/runtime/tracking` 类不作为兼容承诺。
- 建议拆出纯 Java 21 的 `api` 模块，包含 UUID/时间/快照/请求/结果和接口；Paper 的事件及服务注册放在 `api-paper`。不向 `common` 或 `protocol` 引入平台类。
- 通过 Bukkit `ServicesManager` 注册/获取服务，依赖插件在 `plugin.yml` 中声明 `depend: [ManhuntUniversal]`，采用 `compileOnly` 引用 API，不将其再次打包进自身 JAR，避免类身份重复。
- API 使用独立版本和能力查询；写操作明确要求服务器主线程。公开数据不含 NMS、Fabric 类型或版本特有实现。
- 若未来需要客户端自定义显示，再单独设计客户端能力协商与注册接口，不提前把网络内部实现列为公共 API。

参考：[ServicesManager](https://jd.papermc.io/paper/1.21.11/org/bukkit/plugin/ServicesManager.html)、[Paper 自定义事件](https://docs.papermc.io/paper/dev/custom-events/)。

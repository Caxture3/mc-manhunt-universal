# 结构与传送门追踪的性能

## 当前查询流程

指南针显示每秒更新；重定位查询通过主线程队列执行，每 tick 最多执行一个排队操作。队列分散任务，并不使单次世界查询异步或可中断。

| 目标 | 当前实现 |
| --- | --- |
| 村庄 | 分别定位五种村庄类型，每个类型占一个队列操作，最后取水平距离最近者 |
| 下界堡垒、堡垒遗迹 | 每次重定位调用一次 `World.locateNearestStructure`，`findUnexplored=false` |
| 跨维度指路的传送门 | 查找玩家当前世界内最近的下界传送门 POI；不是遗迹传送门结构，也不逐方块扫描 |

结构世界优先使用当前或该维度最近访问的世界；跨主世界／下界、没有该世界位置记录时，搜索原点按 8:1 转换。跨维度情况下，先找到目标结构，再用当前位置附近的传送门提供方向。

26.3 的传送门查询使用 `World.locateNearestPoi`；1.21.11 使用缓存反射绑定调用原版 `PoiManager.findClosest`。两版的实际世界查询都在主线程执行，反射绑定只初始化一次。

默认重定位条件为相对上次搜索原点移动至少 512 格，并且距上次查询至少 30 秒，两者同时满足才重查。首次选择、切换目标和切换维度等状态失效也会发起搜索。没有找到的结果也会保存，不会每秒重复查询。

默认 `tracking-search-radius-blocks=4096` 同时用于结构和传送门查询。结构查询传入 `ceil(4096/16)=256`，但原版的结构搜索参数不能当作严格的方块半径边界；具体结构的布局算法可能检查更远范围。传送门 POI 的 4096 格查询本身也覆盖很大范围。缓存按玩家保存，多名玩家可能重复搜索同一区域。

这些是从代码确认的开销路径；没有服务器运行时采样，不能断言某一条路径占实际卡顿的百分比。

## 已做的调整

切换或停止追踪结构、目标被重新锁定时，仅取消该玩家的结构查询，不再同时删除传送门结果和正在排队的传送门查询。同维度的传送门搜索与目标结构类型无关，可以沿用既有移动距离／冷却缓存。换世界、退出对局和功能失效等完整清理仍会使相关缓存失效。

这减少反复切换目标带来的重复搜索，不会限制首次大半径查询的耗时，也没有把世界访问改为异步。

## 后续优化方向（尚未实施）

1. 为相同世界和搜索区域建立共享缓存与请求合并，分别缓存成功和未找到结果。缓存需检查距离范围、传送门失效和世界卸载，不能简单复用任意玩家的“最近”结果。
2. 为传送门建立分批读取的 POI 索引，按每 tick 查询数量与时间预算逐步推进，复用已知传送门；完整搜索结束前保留“正在定位”状态。仅把现有大查询隔几 tick 执行，仍会在执行的那一 tick 卡顿。
3. 需要异步时，主线程提取不可变数据，后台只做距离计算／筛选，回到主线程校验对局、世界、请求版本后提交。把尚未缓存区域的 POI 读取也异步化，需要两个版本独立适配服务器的异步读取能力，现有接口不能直接换线程调用。
4. 可另设传送门搜索半径或“只查询已加载区域”模式。这会改变可发现目标范围；尚未改变现有默认行为。缩小现有 `tracking-search-radius-blocks` 也会同时影响结构搜索。

完整定位、只搜索已加载区域和快速返回任意已知传送门有不同语义，不能以优化名义无提示替换。首次查询的峰值耗时和多人重复查询需要分别处理。

技术依据：[Paper 调度与线程安全](https://docs.papermc.io/paper/dev/scheduler/)、[1.21.11 World 定位接口](https://jd.papermc.io/paper/1.21.11/org/bukkit/World.html)、[26.3 World 定位与 POI 接口](https://jd.papermc.io/paper/26.3/org/bukkit/World.html)。

# 结构与传送门追踪的性能

## 查询方式

指南针距离文本按 `tracking-distance-refresh-seconds` 更新，默认 1.0 秒，支持 0.1～60.0 秒；背包维护、解锁通知及选择界面仍每秒更新。大范围重定位默认要求相对上次搜索原点移动至少 512 格，且经过至少 30 秒；首次选择、切换目标、换维度等也会触发查询。切换结构目标会保留同维度传送门缓存。缓存未找到结果，不会每秒重查整个范围。

## 距离刷新与最近结构校正

```text
/mhu config tracking-distance-refresh-seconds 0.1
```

数值为有限小数，默认 1.0，最小 0.1，最大 60.0。按 20 TPS 向上取整，例如 0.1 秒为 2 tick，0.11 秒为 3 tick；服务器掉 TPS 时实际秒数也会变长。修改即时生效，列表单击会预填带末尾空格的命令，沿用现有权限和原子保存。

距离刷新只读当前玩家位置和已有追踪数据，不修复背包、不重发 Dialog、不读取结构元数据、不发起原版定位或 POI 搜索。较长间隔会每秒重发缓存文本以防客户端 ActionBar 淡出，只有到期才更新距离。

旧实现可能在进入较近结构后仍保留旧目标；原版定位点也不代表最近建筑部分。现在维护一个最多 512 条、32768 个部件包围盒及刷怪笼坐标的结构观察索引，将原版查询结果及附近已生成的结构实际部件按当前坐标重新比较。通常站在已确认的结构部件中显示距离 0；下界要塞有有效烈焰人刷怪笼时显示到刷怪笼的距离。不会因整体包围盒覆盖了结构之间的空地，就把空地当成结构内部。

每秒仅为同维度追踪者请求当前及周围已加载的 3×3 区块元数据，合并重复请求并缓存探测结果 30 秒。每 tick 最多执行两次元数据操作；若结构起始区块尚未加载，仅使用 Paper 异步补读被引用、已生成的起始区块，最多两项并发，禁止生成新地形。所有引用已加载后才调用结构读取接口，避免隐式同步加载。结束或卸载会废弃观察结果，实际 I/O 完成前仍占用配额。

这能优先选取已经确认的更近结构，并纠正旧目标在远处的问题。没有观测到的远处结构仍依赖原版定位和原重定位条件，不保证每次移动后瞬时穷尽整个搜索半径。结构几何来自生成元数据，不按玩家摆放的方块识别仿制建筑。

### 下界要塞的烈焰人刷怪笼

先按上述逻辑选定要塞，再以玩家当前位置的三维距离选择这座要塞内最近的已确认烈焰人刷怪笼；不因另一座要塞的刷怪笼更近而换目标。没有有效刷怪笼，或候选超出配置半径时，沿用原结构位置，不需要新增开关或客户端更新。

两版适配器从原版 `MonsterThrone` 部件读取刷怪笼候选坐标，使用原版坐标变换处理朝向。附近已加载区块内、位于实际结构部件中的烈焰人刷怪笼也可成为候选。候选只代表可能的位置，主线程必须检查真实方块为刷怪笼且实体类型为烈焰人，不能把已经破坏的刷怪笼或其他生物刷怪笼当成目标。

原版定位结果对应区块、结构起始区块及候选所在区块共用最多两项并发的异步无生成加载；不扫描要塞方块、不生成缺失地形。检查尚未完成或已生成区块无法读取时，仍使用结构位置。已加载的已知刷怪笼每秒复核，破坏或改变类型后移除，重新选取其余有效刷怪笼或回退。已卸载区块保留上次确认结果，不为每秒复核强制加载；再次读取后才可确认其中后续变化。跨维度时仍先引导到当前维度的传送门。

| 目标 | 实现 |
| --- | --- |
| 村庄 | 原版定位五种村庄，每种占一个同步队列操作，最后取水平距离最近者 |
| 下界要塞 | 原版 `World.locateNearestStructure`，`findUnexplored=false`；已确认要塞优先追踪其最近烈焰人刷怪笼，无有效目标时回退 |
| 堡垒遗迹 | 原版 `World.locateNearestStructure`，`findUnexplored=false` |
| 跨维度传送门 | 按区块列读取下界传送门 POI，从近到远分批推进，后台筛选不可变坐标 |

结构世界优先使用当前或该维度最近访问的世界；没有位置记录时，主世界／下界的搜索原点按 8:1 转换。跨维度情况下，先找到目标结构，再用玩家当前世界内最近的传送门提供方向。传送门不是遗迹传送门结构，不逐方块扫描，也不要求与目标世界的某扇门已配对。

`tracking-search-radius-blocks` 默认 4096，范围和原配置含义保持不变。结构定位传入 `ceil(radius/16)`；原版定位参数不是严格的方块半径，具体布局算法可能检查更远处。传送门按原版整数 BlockPos 原点，在配置半径的三维球内取欧氏距离最近的 POI，保留搜索未加载区块内已有传送门的能力。

## 共享缓存与请求合并

结构查询仅合并世界、目标、原点、半径完全相同的请求，不把某个玩家的最近结果直接当成附近所有人的最近结果。成功结果缓存 5 分钟，未找到缓存 15 秒，最多 512 条。原版结构定位仍在主线程同步执行；缓存和合并减少重复调用，并未使单次原版定位可中断。

传送门的相同完整请求共用搜索；不同原点也共用世界／区块列 POI 快照。快照及完整查询结果缓存 30 秒，分别最多 32768 列和 512 条；快照缓存另有 262144 个坐标的上限，按最近使用淘汰。完成或取消后释放订阅，首位请求者退出不会取消其他玩家仍在等待的共享工作。

## 分批与异步

每 tick 所有传送门请求合计最多推进 **64 个区块列**，主线程推进采用 **2 ms 软预算**，多个请求轮流获得处理机会。已经得到足够接近的候选时，只有确认所有未搜索列的距离下界都不可能更近，才提前结束；搜索过程中维持正在定位状态或沿用既有结果。

每个版本适配器通过缓存反射绑定调用原版 `PoiManager.getInChunk`，在主线程完整消费并关闭单列 POI 流，输出不可变整数坐标列表。未缓存列可能同步读取 POI 存储并等待磁盘，但不加载或生成实际方块区块。

后台任务只做球形范围筛选和三维距离计算，不访问 Bukkit、世界、玩家、Location 或 NMS 对象。主线程非阻塞轮询已完成任务，再验证共享工作和玩家请求版本；过期结果不能覆盖新目标或新对局。使用插件绑定的 Bukkit 异步调度，不创建常驻线程池。

**2 ms 不是硬性耗时保证。** 单列同步 POI I/O 不能被中断，在慢磁盘上仍可能超过预算。范围内没有门时，完整搜索会跨多个 tick 等待；不以“只查已加载区域”或“返回任意已知门”替换完整最近目标搜索。

## 失效与生命周期

门的创建、门体物理变化、消失和框架破坏／爆炸会合并失效请求。普通黑曜石只有邻接实际门体时才作为框架处理；边界邻接区块未加载时保守失效，不为检查邻接方块加载区块。每个受影响列在最后一次变化后至少等待两 tick，再清除其快照和受影响世界的完整传送门查询，避免提前读到尚未更新的 POI。

世界卸载时清理该世界的快照、查询、等待中的事件及相关玩家状态。离线、切换世界、功能关闭、淘汰或结束／停止对局会取消相应订阅；对局和插件清理会丢弃仍在计算的结果。已加载区块中的最终候选还会检查是否仍为门体，不会为验证加载区块。

## 验证边界

针对性检查覆盖随机几何对照、负坐标、半径边缘、提前剪枝、共享取消、正负缓存／淘汰／过期、全局列数／软时间预算、公平轮换、真实后台线程、快照复制、晚到结果、读取失败和事件失效合并。两版反射成员签名由各自映射 JAR 字节码核对，编译与实际游戏运行验证分别记录。

尚未进行实服性能采样，因此没有声称 TPS 改善比例或定位耗时上限。首次原版结构查询与单列 POI 冷读取仍是需要在真实服务器上观察的开销。
